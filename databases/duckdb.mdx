Pick a `.duckdb` file to open a database, or a `.parquet`, `.csv`, `.tsv`, `.json` or `.ndjson` file to read it where it sits. DuckDB 2.0.0 is compiled into the driver, so nothing runs as a server unless you point the connection at one. A `.duckdb` file the connection creates or attaches stays readable by DuckDB 1.x.

## Quick setup

<Steps>
  <Step title="Create the connection">
    Click **New Connection…** or press `Cmd+N`, then choose **DuckDB**.
  </Step>
  <Step title="Choose a file">
    Leave **Connection Type** on **Local File** and click **Browse…**, or **New…** to name a `.duckdb` file that does not exist yet. Type `:memory:` in the field instead for a database that lasts as long as the session.
  </Step>
  <Step title="Connect">
    Click **Save & Connect**.
  </Step>
</Steps>

## What the file field accepts

| Path | What you get |
|-------|-------------|
| `.duckdb`, `.ddb`, or a DuckDB or SQLite file under any other name | The database in that file. A path that does not exist yet is created |
| `.parquet`, `.csv`, `.tsv`, `.json`, `.jsonl`, `.ndjson`, also gzip or zstd compressed | An in-memory database holding two read-only views over the file, one named `file` and one named after the file. A path that does not exist is reported instead of created |
| `:memory:` | An empty database, discarded on disconnect |

In Local File mode the path is the whole connection, and it is required; the form shows no host, port or Database field, and no Network tab.

Double-click a `.duckdb` or `.ddb` file in Finder to open it here. `.parquet` files list TablePro under **Open With** rather than taking the association; to make a double-click open them here, select one in Finder, press `Cmd+I`, set **Open with** to TablePro, and click **Change All…**. `.csv`, `.tsv`, `.json` and `.ndjson` open from the connection form only.

A DuckDB database carries `DUCK` eight bytes in, so a database opens under any name: drag `warehouse.db` onto a window and it reaches this driver rather than SQLite. The data formats need their extension either way, because the reader is chosen from it. Installing the plugin is offered first when it is not already there.

## Remote (Quack)

Quack is DuckDB's client-server protocol, served by `quack_serve`. Set **Connection Type** to **Remote (Quack, experimental)**:

| Field | Value |
|-------|-------|
| **Host** | Server address. Required |
| **Port** | `9494` by default |
| **Token** | The token the server was started with |
| **Database Alias** | The name the remote is attached under. Pre-filled with `remotedb` |
| **SSL Mode** | **Automatic** by default. See [SSL/TLS](#ssl%2Ftls) |
| **CA Certificate** | Under Verify Identity only. The PEM file of the CA that signed the server's certificate. Optional |
| **Certificate Fingerprint** | Under Verify Fingerprint only. The SHA-256 fingerprint of the server's certificate. Required |

**Save & Connect** attaches the remote to an in-memory DuckDB. Reach it through the alias: `SELECT * FROM remotedb.main.orders`.

For a server this Mac cannot reach directly, Remote mode adds a **Network** tab with [SSH Tunnel](/connections/ssh-tunneling), [Cloudflare Tunnel](/connections/cloudflare-tunnel), [SOCKS Proxy](/connections/socks-proxy) and [Tunnel Command](/connections/tunnel-command). **Host** and **Port** stay the server's own, named as the far end of the tunnel reaches it: `localhost` for a server on the SSH server itself. Then pick the SSL Mode from [Through a tunnel](#through-a-tunnel).

<Info>
The macOS build links neither the `quack` extension nor `httpfs`, which carries HTTPS under every SSL Mode but Verify Fingerprint. DuckDB downloads each from `extensions.duckdb.org` the first time a connection needs it and caches it under `~/.duckdb`, so that connect needs to reach that host.
</Info>

## Connection URL

```text
duckdb:///path/to/database.duckdb
quack://host:9494/alias
quack://host:9494/alias?sslmode=verify-full
quack+ssh://deploy@bastion.example.com/localhost:9494/alias
```

`sslmode` sets **SSL Mode**, and a connection behind an SSH tunnel copies as `quack+ssh://`. [DuckDB remote](/connections/urls#duckdb-remote) lists the values, and what happens to Verify Fingerprint, which no URL carries.

## Databases and schemas

A connection opens one database named after the file: `analytics.duckdb` becomes `analytics`, schema `main`. `ATTACH` a second file and it joins the sidebar as a sibling database after a refresh:

```sql
ATTACH 'warehouse.duckdb' AS warehouse;
```

Press `Cmd+K` to move between them, in place, with no reconnect. An `ATTACH` typed in the editor lasts until the next connect. To keep a file attached, add it under **Attached Databases** in the connection's **Options**: every connect attaches it again, named after its file without the extension, and a file that is missing is named in a warning while the rest attach. With **Open the File Read-Only** on, they attach read-only as well. `system` and `temp` are hidden, and with them `information_schema` and `pg_catalog`.

Any connection can also read a file straight from SQL:

```sql
SELECT * FROM 'data.csv';
SELECT * FROM read_parquet('analytics.parquet');
```

## Sharing the file with another process

One process writes a DuckDB file at a time, and the lock lasts as long as the connection. While a tab is open on `sales.duckdb`, `duckdb sales.duckdb` in a terminal is refused, and so is a notebook, a dbt run, or a second TablePro window.

Three ways out, in **Options** on the connection:

| Setting | What happens | Pick this when |
|---|---|---|
| **Release the File Lock After** | The file is handed back once the connection has been idle that many minutes, and taken again on the next query. `0`, the default, keeps it | A script or a scheduled job needs the file while you are reading it |
| **Open the File Read-Only** | The file is opened read-only, which several processes can do at once. Writes are refused by the engine | Two or more readers, and nothing writing |
| Neither | The lock is held for the life of the connection | Nothing else touches the file |

**Database ▸ Release File Lock** hands it back now, without ending the session. The tabs, the schema cache and the row you were on all stay; the next query takes the file again.

A release is refused, with the reason, while the session holds anything reopening would destroy: an open transaction, a temporary table or view, a database attached from the editor, or a changed setting. The connection's own **Attached Databases** attach again on reopen. Commit the transaction or drop the temporary table and the release goes through.

Read-only is not a way to keep writing from somewhere else. A read-write connection blocks every other process, read-only ones included; a read-only connection blocks writers. Two readers work, a reader and a writer do not.

Releasing hands the file to whoever wants it next, which may not be you. A query run after another process has taken it fails until that process lets go; reconnect once it has.

## Back up and restore

**File > Backup Dump…** runs over the open connection. It copies the whole database into a `.duckdb` file, or exports it as a folder of Parquet files. **File > Restore Dump…** takes the `.duckdb` file. For the folder, and what each format carries, see [Backup & Restore](/features/backup-restore#what-a-dump-carries).

## SSL/TLS

A local file has no TLS. A remote connection's **SSL Mode** sits on the General tab with the other Remote fields and starts on **Automatic**. Leave it there unless the server's certificate comes from a private CA or from `quack_serve` itself. No mode falls back to another: a mismatch stops the connect with a message naming the setting to change.

| SSL Mode | What the connection does | Pick it for |
|---|---|---|
| **Automatic** | Plain HTTP to `localhost`, `127.0.0.1` and `::1`. HTTPS to any other host, with the certificate checked against `/etc/ssl/cert.pem` and the host name | A server on this Mac, or one with a public certificate |
| **Disabled** | Plain HTTP to any host | A plain HTTP server on another machine |
| **Required (skip verify)** | HTTPS, with no certificate check | Testing. The token goes to whichever server answers |
| **Verify Identity** | HTTPS, with the certificate checked against `/etc/ssl/cert.pem` plus **CA Certificate**, and the host name | A certificate from a private CA, such as one mkcert made |
| **Verify Fingerprint** | HTTPS, with the certificate matched against **Certificate Fingerprint**. No name is checked | The certificate `quack_serve` generates, or any self-signed one |

### Trusting a private CA

DuckDB never reads the macOS keychain. A CA trusted there, by `mkcert -install` or in Keychain Access, does not make its certificates pass under Automatic. Give DuckDB the CA file instead:

<Steps>
  <Step title="Find the CA file">
    Use the PEM certificate of the CA that signed the server's. For mkcert that is `rootCA.pem`, in the folder this prints:

    ```bash
    mkcert -CAROOT
    ```
  </Step>
  <Step title="Choose it">
    Set **SSL Mode** to **Verify Identity**, click **Browse…** beside **CA Certificate**, and choose the file.
  </Step>
</Steps>

The file has to be PEM. A DER file is refused before DuckDB dials the server; convert it with `openssl x509 -inform der -in ca.der -out ca.pem`.

The connection then trusts that CA on top of `/etc/ssl/cert.pem` for every HTTPS read it makes, `read_parquet('https://…')` in its editor included. Other connections are unaffected. With **CA Certificate** left empty, Verify Identity checks against `/etc/ssl/cert.pem` alone, and uses HTTPS even to `localhost`.

### Pinning the server's certificate

Started without a certificate of its own, `quack_serve` generates one that names no host, so no CA check can pass it. Set **SSL Mode** to **Verify Fingerprint** and paste the certificate's SHA-256 fingerprint into **Certificate Fingerprint**. On the server, the `ssl_fingerprint` column holds it:

```sql
FROM quack_server_list();
```

For a certificate file, `openssl` prints the same value:

```bash
openssl x509 -noout -fingerprint -sha256 -in cert.pem
```

The field takes the 64 hex digits with or without colons, and with or without `sha256:` in front. Once the server has a new certificate, the pin fails until you paste the new fingerprint.

### Through a tunnel

A tunnel hands DuckDB a port on `127.0.0.1` in place of the server's name, so no mode checks the certificate's name there. **Host** on General still decides what Automatic does.

| The server | SSL Mode |
|---|---|
| `quack_serve` on `localhost` where the tunnel lands, serving plain HTTP | **Automatic**, with **Host** set to `localhost`. Nothing off that machine reaches the server, and the tunnel encrypts the hop. Prefer this setup |
| HTTPS, on any host | **Verify Fingerprint**, or **Required (skip verify)** to encrypt without a check |
| Plain HTTP, on another host | **Disabled** |

Verify Identity, and Automatic with any **Host** but `localhost`, `127.0.0.1` or `::1`, are refused before DuckDB dials, with a message naming the modes that work.

## Limitations

- A DuckDB file takes one writer at a time. A connect against a file another process holds fails, naming that process and its process ID. Quit the `duckdb` CLI, the Python process or the other TablePro window first, or set **Release the File Lock After**.
- A data file opened through **Browse…** is read-only, and the file on disk is left byte for byte identical. To change its contents, open a `.duckdb` database and run `CREATE TABLE t AS SELECT * FROM 'data.parquet'`.
- Remote (Quack) lists no tables in the sidebar. Write them out by name through the alias.
- Local File has no tunnel. To reach a file on another machine, serve it there with `quack_serve` and connect in Remote mode.
- Quack takes no client certificate. **Token** is the only credential a remote connection sends.
- **Required (skip verify)** turns the certificate check off for every HTTPS read the connection makes, `read_parquet('https://…')` in the editor included. Pin the server with **Verify Fingerprint** to keep those reads checked.
- No creating or dropping a database. `ATTACH` is the way to reach a second file.

## Troubleshooting

### No file at …

A data-file path that is not there. Only `.duckdb` and `.ddb` are created on demand. Re-pick the file with **Browse…**.

### DuckDB opened the file but reported no catalog to browse

The file opened and exposed nothing to list. Check that it is a DuckDB database and not a file with a borrowed extension.

### … is using sales.duckdb

Another process holds the file. The message names it and its process ID. Quit it, or turn on **Open the File Read-Only** when the message says read-only would get in, which it does when the other process is itself a reader.

### The database file is no longer at …

The file moved or was deleted while the connection was idle with its lock released. Point the connection at the new path, or restore the file, then reconnect.

### Port must be a number between 1 and 65535

**Port** holds something else. The Quack default is `9494`.

### DuckDB could not install its … extension

The first remote connect downloads `quack`, and `httpfs` for HTTPS, from `extensions.duckdb.org`, and this Mac could not reach that host. DuckDB's own reason follows the message. Allow the host through the firewall or proxy, then connect again; once installed, the extension loads with no network.

### DuckDB could not verify the server's certificate

The server's certificate was signed by a CA that neither `/etc/ssl/cert.pem` nor **CA Certificate** holds, or it names another host. A CA trusted only in the macOS keychain counts as neither. Choose the CA file under **Verify Identity**, or pin the certificate under **Verify Fingerprint**, as [SSL/TLS](#ssl%2Ftls) shows.

### The server uses HTTPS, and this connection sent plain HTTP

**SSL Mode** is Disabled, or Automatic with a local **Host**, and the server speaks TLS. Set it to **Verify Identity**, or to **Verify Fingerprint** for a self-signed certificate. Through a tunnel, use **Verify Fingerprint** or **Required (skip verify)**.

### The server did not answer the TLS handshake

The connection used HTTPS, and the server serves plain HTTP or is not a Quack server. Check how `quack_serve` was started. For plain HTTP, set **SSL Mode** to **Disabled**.

### The server's certificate does not match the Certificate Fingerprint

The server now presents a different certificate from the one pinned, or another server answered. Read `ssl_fingerprint` again from `FROM quack_server_list();` on the server and paste it into **Certificate Fingerprint**.

### The Certificate Fingerprint is not a SHA-256 fingerprint

**Certificate Fingerprint** holds something other than 64 hex digits, a 40-digit SHA-1 fingerprint for instance. Copy it again from `quack_server_list()`, or from `openssl x509 -noout -fingerprint -sha256 -in cert.pem`.

### The CA Certificate at … is not a PEM certificate

The file under **CA Certificate** is DER, or not a certificate at all. Convert a DER file with `openssl x509 -inform der -in ca.der -out ca.pem`, then choose `ca.pem`.

### TablePro could not read the CA Certificate at …

The file moved, or its permissions keep it from being read. The reason follows the path. Choose the file again with **Browse…**.

### DuckDB could not read the CA Certificate

The file under **CA Certificate** starts like PEM, and DuckDB still rejected it. Check that it holds whole `-----BEGIN CERTIFICATE-----` blocks, or export the CA again as PEM.

### Verify Identity does not work through a tunnel

**SSL Mode** is Verify Identity and the Network tab has a tunnel selected. DuckDB dials the tunnel on `127.0.0.1`, so the certificate would be checked against that rather than the server's name. Set **SSL Mode** to **Verify Fingerprint**, or to **Required (skip verify)**.

### Automatic does not work through a tunnel to …

**Host** is not `localhost`, `127.0.0.1` or `::1`, so Automatic would use HTTPS and check the certificate against `127.0.0.1`. Set **SSL Mode** to **Verify Fingerprint**, **Required (skip verify)**, or **Disabled** for a plain HTTP server. Or run `quack_serve` on `localhost` where the tunnel lands and set **Host** to `localhost`.
