Tables show as tables and rows as grid rows, with the row key in `_key` and one column per `family:qualifier`. The plugin talks to the Bigtable REST API. The editor takes request lines such as `GET events/user#42`, not SQL.

## Quick setup

Click **New Connection…**, select **Google Cloud Bigtable**, pick an **Auth Method**, then click **Save & Connect**.

With a service account key, **Project ID** can stay empty: the project comes from the key. With **Instance ID** empty, the connection opens the project's first instance, and the database switcher lists the others.

## Connection settings

| Field | Description |
|-------|-------------|
| **Auth Method** | Service Account Key, or Application Default Credentials |
| **Service Account Key** | A path to the JSON key file, or the JSON pasted in. Stored in the Keychain |
| **Project ID** | The Google Cloud project. Taken from the key or from Application Default Credentials when empty |
| **Instance ID** | The Bigtable instance. The first one in the project when empty |
| **App Profile ID** | Options tab. Routes reads and writes through that app profile. The instance's default profile when empty |

## Authentication

| Auth Method | What is sent |
|-------------|--------------|
| **Service Account Key** | An OAuth token signed with the key. Reading needs the Bigtable Reader role, editing the Bigtable User role |
| **Application Default Credentials** | The token from `gcloud auth application-default login`, or from the file `GOOGLE_APPLICATION_CREDENTIALS` names |

When IAM refuses an operation, the error says **Permission denied** and names the operation, rather than showing an empty table.

## Browsing tables

The sidebar lists the instance's tables. Bigtable has no fixed columns, so the columns are the `family:qualifier` pairs found in the first rows. A cell a row does not have shows as missing, not as NULL. Each cell shows its newest version.

Keys, qualifiers and values are bytes. Text shows as itself. Anything else shows as `b64:` followed by base64, which reads back to the same bytes, so a binary key can still be filtered on and edited. A value that is not text goes to the grid as bytes and shows as hex.

Rows come in ascending key order. Clicking a column header sorts the rows on screen, since the REST API has no other order. A later page starts after the last key of the page before; a page jumped to directly skips the rows before it by reading their keys alone.

Bigtable keeps no row count. Counting reads every key, so it runs only when you ask for the count.

## Filtering

A filter on `_key` becomes a row range, which reads only the rows it names:

| Operators on `_key` | What Bigtable reads |
|----------|--------------------|
| equals, in list | Exact keys |
| starts with | The key range of that prefix |
| greater than, greater or equal, less than, less or equal, between | A key range |
| not equals, contains, not contains, ends with, REGEX | A row key regex, over every row |

A filter on a `family:qualifier` column keeps or drops whole rows by that cell's newest value:

| Operators on a column | What Bigtable runs |
|----------|--------------------|
| equals, not equals, contains, not contains, starts with, ends with, in list | A value regex |
| REGEX | The pattern as written, in RE2 syntax |
| greater than, greater or equal, less than, less or equal, between | A value range, compared byte by byte |
| is empty, is not empty | An empty value regex |
| is NULL, is not NULL | Whether the row has the cell |

Values are compared as bytes, so `9` sorts after `10`. Several filters combine with AND or OR. Key ranges cannot be ORed with column filters; use `=`, starts with or REGEX on `_key` there. The raw filter takes a `RowFilter` from the Bigtable REST reference, with bytes in base64.

## Editing

Grid edits are row mutations, one per row, applied atomically.

| Change | Request |
|--------|---------|
| New row | `PUT` with the key you typed in `_key` and every cell you filled |
| Edited cells | `PUT` with the changed cells |
| Removed cell | The cell set to `null` in the `PUT` |
| Deleted row | `DELETE` on the key |

A new row needs a `_key` and at least one cell, and a cell needs a column family the table already has. Cells are written with the server's clock.

## Request editor

| Request | What it does |
|---------|--------------|
| `GET events/user#42` | One row |
| `SCAN events/user#?limit=20` | Rows whose key starts with the prefix, 100 when no limit is given |
| `READ events {"rowsLimit": "10"}` | A ReadRows body from the REST reference, sent as written |
| `PUT events/user#42 {"profile:name": "Ann"}` | Sets cells. `null` deletes a cell, and `b64:` text writes bytes |
| `DELETE events/user#42` | Deletes the row |
| `DELETE events/user#42 profile:name` | Deletes one column of the row |

The table goes before the first slash. A key with spaces or a slash goes in JSON quotes, `GET events/"a b/c"`, and a binary key as `b64:<base64>`.

## Limitations

- No GoogleSQL. Use the request editor.
- No reverse scans: the REST API reads rows in ascending key order only.
- Only the newest version of each cell is shown or written.
- Tables and column families are not created or changed from TablePro.
- Export fixes its columns from the first page. Columns that appear only later go into an `__extra__` column as JSON.
- The plugin is registry-only. It is not on iPhone or iPad.

## Troubleshooting

### Permission denied: …

The credential's IAM role does not cover the operation. Reading needs Bigtable Reader, editing Bigtable User.

### No instance in the project

The error reads "Project … has no Bigtable instance". The project in **Project ID** or in the key has none. Check the project, or fill in **Instance ID**.
