Server commands on this page, such as `license install`, run in a one-off container. [Docker Compose](/self-hosted/docker-compose#run-a-command) and [AWS Fargate](/self-hosted/aws#run-a-command) show how on each platform.

## License

The license file is one signed line of text that TablePro issues for your API address. It sets the seats, the features and the end of the license, and every seat includes Pro on the Mac. A staging server needs a file of its own for its own address.

`license install <file>`, or `license install -` to read the file from standard input, checks the file and installs it in place of the one installed. It refuses a file that:

- was not signed by TablePro, or names another address than `https://` plus `API_HOST`;
- is past its grace;
- is older than the installed file of the same license;
- is perpetual, and its maintenance ended before this release.

`license status` prints the license and file IDs, the type, the seats, the end and the grace, or a perpetual file's end of maintenance, the address, the features and the state, then `seats taken: <taken> of <seats>`. With no file installed, it prints `no license: no license is installed`.

### Renew

A renewal, or a change of seats, is a new file of the same license. Sign in at [account.tablepro.app](https://account.tablepro.app) with the email address you paid with: **Billing** lists your licenses under **Self-hosted licenses**, each with **Download**, and an email tells you when a new file is there. Install it as above, or let the server fetch it. A file with fewer seats than are taken keeps everyone who has one, and no one new signs in until enough seats are freed under [Remove someone](/self-hosted/roles#remove-someone).

To fetch renewals, set `LICENSE_RENEWAL=on`. It is off by default, and with it off the server makes no call to tablepro.app. Once a day, and at each start, the server asks `https://api.tablepro.app/v2/licenses/latest` for the newest file of its license. The first fetch runs about a minute after the server starts. It sends the installed file and nothing else: no seat count, usage or version.

- The server fetches renewals only from a file tablepro.app issued through **Billing**. An evaluation file fetches nothing: install the first file from **Billing** by hand, and the server fetches from then on. Until then, each try logs `license renewal failed`.
- It installs the answer only when it is a later file of the same license for the same address, after the checks `license install` makes. The audit log records it as `license.installed` with `source` `renewal`.
- A failed fetch logs `license renewal failed` and tries again the next day. The installed file keeps working to the end of its grace, and the file from **Billing** still installs by hand.
- A monthly license needs it. A server that cannot reach tablepro.app takes a yearly or longer term.

Behind a proxy, set `HTTPS_PROXY`, such as `http://proxy.example.com:3128`. Every outbound call of the server then goes through it, the OIDC identity provider's too: list an IdP inside your network in `NO_PROXY`. A proxy that inspects TLS needs its CA in `SSL_CERT_FILE`, as under [Settings](/self-hosted/settings#identity-provider).

### When a license ends

A file with an end date has a grace after it, written into the file: 21 days for a monthly license, 30 days for every other.

| State | From | What works |
|---|---|---|
| `active` | Until the end date | Everything |
| `grace` | The end date, until the grace ends | Everything. The Mac shows the grace under **License** in **Settings > Account** |
| `lapsed` | The end of the grace | Pulls, administration, and key changes such as Sign Out, approving and removing devices, recovery and resets. The server refuses data uploads with `license_expired`, Team Library publishes included, and changes wait on each Mac; see [Company server](/features/company-server#what-is-different-on-a-company-server) |

A perpetual file has no end date. It covers every release dated up to its end of maintenance, and keeps them running for good. `migrate up`, `serve` and `license install` refuse a later release and name the last date the file covers; `migrate up` refuses before it changes the schema. Extending maintenance is a new file with a later date.

## Upgrades

Read the release's notes under [Self-hosted releases](/self-hosted/releases) first.

- **One minor version at a time**, such as 0.1 to 0.2, then 0.2 to 0.3. Each release's migrations only promise that the release before it runs on the new schema. To skip a minor version, stop the old server first.
- **Back up first**, as under [Back up](#back-up). Migrations only go forward, so going back to the earlier release means restoring the backup taken before the upgrade.
- **A perpetual license** must cover the new release; `migrate up` refuses it otherwise, before it changes anything.

With Docker Compose, set `TABLEPRO_IMAGE` in `.env` to the new digest, then run the migrations while the old server still serves, and start the new one only once they exit 0:

```bash
docker compose run --rm migrate
docker compose up -d --no-deps app
```

<Warning>
A plain `docker compose up -d` removes the old `app` before `migrate` runs, so a migration that fails leaves nothing serving.
</Warning>

On AWS, set the new digest in both task definition files, `tablepro-cloud` and `tablepro-cloud-license`, and register a new revision of each. A license task left on the old revision installs the next file with the old release. Then deploy the service with the first:

```bash
revision=$(aws ecs register-task-definition --cli-input-json file://ecs-task-definition.json \
  --query 'taskDefinition.revision' --output text)
aws ecs register-task-definition --cli-input-json file://ecs-license-task-definition.json \
  --query 'taskDefinition.revision' --output text
aws ecs update-service --cluster tablepro --service tablepro-cloud --task-definition "tablepro-cloud:$revision" \
  --query 'service.serviceName' --output text
```

A new task whose `migrate` fails never starts `app`. The old task keeps serving and the circuit breaker rolls the deployment back, but it cannot undo a migration that ran.

Wait for the rollout, then check which revision it ended on:

```bash
aws ecs wait services-stable --cluster tablepro --services tablepro-cloud
aws ecs describe-services --cluster tablepro --services tablepro-cloud \
  --query "services[0].deployments[?status=='PRIMARY'].[taskDefinition,rolloutState]" --output text
```

It prints the new revision and `COMPLETED`. A deployment the circuit breaker rolled back is stable too, on the old revision. Last, a one-off `version`, as under [Run a command](/self-hosted/aws#run-a-command), prints the new release.

`migrate up` prints nothing when it succeeds. To check the schema, run `migrate status` as a one-off command: it lists every migration with the time it was applied, or `pending`, and the `river` rows show `yes` in place of a time. After an upgrade, no row is `pending`.

## Back up

Back up the database, and keep the `TABLEPRO_CREDENTIALS` value next to the backups: a database restored without its `identity-tokens` key cannot read the IdP refresh tokens it holds.

With Docker Compose, dump the database, at least before each upgrade:

```bash
docker compose exec -T postgres pg_dump -U tablepro -Fc tablepro > tablepro.dump
```

On AWS, RDS keeps automated backups. Before each upgrade, also take a manual snapshot, and deploy only once it is available. A snapshot name takes letters, digits and single hyphens, and starts with a letter:

```bash
aws rds create-db-snapshot --db-instance-identifier <db-instance-id> \
  --db-snapshot-identifier tablepro-before-0-3-0 --query 'DBSnapshot.Status' --output text
aws rds wait db-snapshot-available --db-snapshot-identifier tablepro-before-0-3-0
```

## Restore a backup

A restore rolls the server's sync data back, while the Macs hold positions past it. A new sync epoch makes every Mac take a fresh copy from the restored server, and a Mac on TablePro Sync then sends back the changes it still holds that the restore lost.

<Steps>
  <Step title="Stop the server">
    `docker compose stop app`, or set the service's desired count to 0.
  </Step>
  <Step title="Restore the database">
    With Compose, into an empty database:

    ```bash
    docker compose exec -T postgres dropdb -U tablepro tablepro
    docker compose exec -T postgres createdb -U tablepro tablepro
    docker compose exec -T postgres pg_restore -U tablepro -d tablepro < tablepro.dump
    ```

    On AWS, restore the RDS instance to a point in time as a new instance, and point `DATABASE_URL` in a new task definition revision at it.
  </Step>
  <Step title="Start a new sync epoch">
    Once, before the server starts: `docker compose run --rm --no-deps app sync new-epoch`, or the same command as a one-off task on AWS. It prints the epoch's ID.
  </Step>
  <Step title="Start the server">
    `docker compose up -d`, or the desired count back to 1.
  </Step>
</Steps>

<Danger>
Everything written to the server after the restore point is lost there. Only what a Mac on TablePro Sync still holds comes back. A Mac without TablePro Sync takes the restored Team Library and drops its newer copy.
</Danger>

Keys come back the same way: each Mac sends back the keys its own account made that the restore lost. Two cases need a person:

- A Mac whose account keys cannot go back shows **Your keys could not be restored**. The person signs out, then uses their recovery key or resets their keys; see [Sync](/features/sync#lost-the-recovery-key).
- A team key that someone else made waits on each teammate's Mac until that person's device sends it back, then sync carries on by itself. A team key that cannot go back ends the team's keys: an owner creates a new team and shares its connections again.

### The restore check

`serve` also checks for a restore by itself, at start and on each new database connection. It compares the database cluster's system identifier and timeline with the ones it stored. A point-in-time recovery, a promoted standby and a dump restored into a new cluster each change one, and the server opens a new epoch at once and logs `the database was restored, so a new sync epoch started and every app refills` at WARN. A storage snapshot, or a restore into the same cluster, changes neither, so run `sync new-epoch` after every restore. A second epoch costs each Mac one more fresh copy and loses nothing.

A connection pooler between the server and PostgreSQL that keeps its own server connections, such as PgBouncer in transaction mode or RDS Proxy, hides a database swapped behind it. Neither reference deploy has one. Behind one, only `sync new-epoch` after every restore opens the new epoch.

The check reads `pg_control_system()`, `pg_current_wal_insert_lsn()` and `pg_walfile_name()`, which PostgreSQL lets every role run. When it cannot, every TablePro Sync call answers 503 `restore_check_unavailable`, Macs without TablePro Sync still get Team Library, and the server logs why at ERROR:

| `msg` | Fix |
|---|---|
| `the restore check cannot read the database's control data, so /v2/sync answers 503 restore_check_unavailable` | The three functions were revoked, or the database has none of them. Run the `grant execute` the log line names, as a superuser |
| `the database is a standby or still recovering, so /v2/sync answers 503 restore_check_unavailable until it is promoted` | Point `DATABASE_URL` at the primary, or promote the standby |
| `the database holds sync writes but no identity for the restore check, so /v2/sync answers 503 restore_check_unavailable until sync new-epoch runs` | Stop the server, run `sync new-epoch`, then start it |

## Lost passkeys

Someone who lost every passkey can still use a synced copy at its provider, such as iCloud Keychain or a password manager. Otherwise, run `passkeys reset` with their address, as a one-off command on [Docker Compose](/self-hosted/docker-compose#run-a-command) or [AWS](/self-hosted/aws#run-a-command):

```bash
docker compose run --rm --no-deps app passkeys reset ada@example.com
```

It deletes every passkey of the account, the owner's included, and ends its portal sessions. App sessions stay. It prints the account's ID and how many it deleted, never the address, and records `account.passkeys_reset` in the audit log. With an SMTP relay set, the person gets an email. They add a new passkey at their next step-up, after the IdP signs them in again; see [Step-up](/self-hosted/sign-in#step-up).

Nobody resets passkeys from the portal.

Moving the portal to another host makes every passkey useless there. After the move, run `passkeys reset` for everyone who has one, starting with the owner and admins.

## Test the mail relay

With the `SMTP_*` settings in place, send yourself one message:

```bash
docker compose run --rm --no-deps app mail test you@example.com
```

It goes straight through the relay, not the server's queue, and prints `The relay at <host>:<port> took the test message <id>.` A failure exits 1 and names the step that failed: connect, tls, authentication, sender, recipient or data. [Email](/self-hosted/settings#email) lists the settings.

## Alerts

The server writes one JSON object per line to standard output, with `level` and `msg`. A command that fails, a `serve` that refuses to start and `migrate up` included, writes one more JSON line to standard error, with `"level":"ERROR"`, `"msg":"command failed"`, `command` and `error`, and exits 1. Wrong arguments print the error and the usage as plain text and exit 2, which a filter on the JSON never sees, so alert on the exit code too:

| Signal | Means |
|---|---|
| `"level":"ERROR"` from `app`, `migrate` or a one-off command. In CloudWatch, the metric filter `{ $.level = "ERROR" }` | Something failed while serving, or a command failed |
| `migrate`, `app` or a one-off command exiting non-zero. On AWS, the EventBridge rule under [Service](/self-hosted/aws#service); with Compose, `die` events from `docker events` | A start, a deploy or a command failed |
| The ALB's `UnHealthyHostCount` at 1 or more for 5 minutes, and `HTTPCode_Target_5XX_Count` | The server is down or failing requests |
| RDS `FreeStorageSpace` under 2 GB, `CPUCreditBalance` running low, `FreeableMemory` | The database is running out of room |

The server also logs these events once a day and at each start. A metric filter `{ $.msg = "license*" && $.level != "INFO" }` catches the license ones and leaves out `license active` and `license renewed`.

| `msg` | Level | When |
|---|---|---|
| `license not installed` | WARN | No license file verifies |
| `license expires soon` | WARN | From 30 days before the end date, unless `LICENSE_RENEWAL=on` |
| `license expired, in grace` | WARN | Past the end date, within the grace |
| `license lapsed, sync pushes refused` | ERROR | Past the grace |
| `license renewal failed` | WARN | With `LICENSE_RENEWAL=on`: no route, a proxy that refused, tablepro.app down, or an answer the server does not take. It tries again the next day |
| `license renewed` | INFO | With `LICENSE_RENEWAL=on`: a later file was installed |
| `license renewal found no newer file` | INFO | With `LICENSE_RENEWAL=on`: nothing newer yet |
| `license maintenance ends soon` | WARN | A perpetual file, in the 30 days before its maintenance ends |
| `idp certificate expiring` | WARN | A trusted SAML signing certificate ends within 30 days |
| `idp certificate expired` | ERROR | A trusted SAML signing certificate has ended, and sign-ins it signs fail |

These events come as they happen:

| `msg` | Level | When |
|---|---|---|
| `passkey added`, `passkey removed` | INFO | Someone added or removed a passkey. Without a relay, these lines and the audit log are the only notice outside the portal. A filter `{ $.msg = "passkey*" }` catches them |
| `passkeys reset` | INFO | `passkeys reset` ran. The command writes it to its own standard error |
| `email off: passkey notices are only in the audit log and these logs; set SMTP_* to send them` | WARN | At start, with no SMTP relay set |
| `an email failed on its last attempt` | ERROR | A passkey notice never went, after about four hours of retries |
| `the mail service refused an email` | ERROR | The relay refused the recipient or the message for good |
| `the database was restored, so a new sync epoch started and every app refills` | WARN | The [restore check](#the-restore-check) found a restored database |
| Three messages that contain `restore_check_unavailable` | ERROR | Sync is down until the cause is fixed; see [The restore check](#the-restore-check) |

`email not sent` at INFO is expected: a self-hosted server sends no email but the passkey notices, and those only with a relay.
